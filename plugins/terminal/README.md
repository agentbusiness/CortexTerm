# Terminal (`terminal`)

PTY terminals running the user's login shell: `terminal.open`, `terminal.write`, `terminal.resize`, `terminal.close`, `terminal.list`, `terminal.snapshot` (VT-parsed screen text) and `terminal.output` events. The UI package is the right pane's Terminal tab (xterm.js with WebGL).

## Shells that outlive the app: `cortexd`

The shells belong to `cortexd`, a small daemon shipped beside `cc-terminal` (`backend/src/daemon.rs`, protocol in `wire.rs`, the plugin side in `client.rs`). The plugin is its client; the `terminal@1` contract and events are unchanged.

- **Start and lifetime.** The plugin starts `cortexd --home $CORTEX_HOME` when nothing answers on `$CORTEX_HOME/run/cortexd.sock` (mode 0600). It forks into its own session and process group at once, so it is not in `children.json` and neither the frame's group kill nor the app quitting reaches it; `run/cortexd.lock` keeps a second daemon out; it logs to `logs/cortexd.log`. It exits by itself after 10 minutes with no living shell and no client.
- **Taking over.** The probe is a *guest* (it sees and closes only its own `/bin/sh`). In `activate` the instance *attaches*: every terminal's output goes to it from then on, and the previous instance gets `taken` and stops serving (blue-green swaps hand over in that instant). `terminal.list` shows the same `term_id`s alive and `terminal.snapshot` repaints them (the Desk and the pane already reuse living ids). `shutdown` only disconnects; nothing is killed.
- **What survives.** Each terminal keeps an opaque `meta` in the daemon: the integration nonce, the folder, the last exit, the Run in progress (as it started), PATH, aliases, functions and the owning session (`marks::Saved`, sent when they change). The next instance resumes the tracker from it and continues the Run's output stream. Output produced while no instance is attached (the last 1 MiB) is replayed to it for the marks and Runs, not published: the snapshot already shows it. A swap can still lose the few lines in flight at the moment of the hand-over; output beyond 1 MiB while nobody is attached is missing from that Run.
- **Flow control.** While attached, the daemon stops reading a shell above 1 MiB unsent and resumes below 256 KiB; output is coalesced to about 16 ms per message. With no client the shell keeps running (the screen stays current; only the last MiB is kept for replay).
- **Close.** `terminal.close` hangs up the shell's process group and the foreground job in the daemon, waits 1.5 s and kills whatever ignored it.
- **Versions.** `wire::DAEMON_VERSION` is bumped whenever the daemon changes. A plugin that meets a daemon of another version with no living shell asks it to quit and starts its own; with living shells it keeps using it (the protocol only grows) and replaces it once its last shell is closed. Shells are never killed for an upgrade.
- If the daemon itself dies, its shells die with it; the plugin reports their exit and the window starts new ones in their folders.

## When a command asks

While a Run is quiet, the plugin asks `cortexd` (daemon version 2, op `tty`) for the terminal's echo and line-mode flags and the newest process of its foreground group. `TermState.ask` then says what the command waits for: `secret` when the terminal stopped echoing in line mode (a password; with an older daemon, a last line ending in `:` that names a password or passphrase), `confirm` for a last line with `[y/n]`, `(yes/no)` and the like (`options` as spelled, `default` the capitalised one), `text` for any other hanging line ending in `:`, `?`, `>`, `)` or `]` after 0.8 s of quiet (`default` the text in a trailing `(...)`). A line redrawn by a carriage return is a progress bar and never asks. `terminal.ask.answer {term_id, text, remember}` sends the text and a return; with `remember` a secret is kept in the macOS Keychain (generic password, service `CortexTerm prompt`, account the ask's `key`: `<program> · <prompt>`, such as `sudo · Password:`). The next time that key asks, the plugin fills it in once and reports the key in `TermState.keychain` for the rest of the Run; the same prompt again within three lines means it was refused, and the ask comes back with `refused: true` instead of a second fill. `terminal.ask.forget {key}` deletes it. These methods and fields are CortexTerm's own additions to `terminal@1` (as `terminal.state` and the Runs are), not part of the standard shared with CortexCode.

## Runs in the graph

Nothing the plugin learns is written to a file (`src/store.rs`; `docs/GRAPH-MODEL.md`, "Terminal"). Every Run goes to the memory plugin (`memory@1`, through the frame):

- **Graph** (OBSERVED layer): `(:Shell {key: term_id, shell, started_ms})-[:ON]->(:Machine)`, `-[:FOR]->(:Session)` when `terminal.open` names a `session_id`; `(:CommandRun {key: run id, command, started_ms, finished_ms, exit_code, duration_ms, lines, bytes, errors, warnings, format, author, fullscreen, usual_ms})` with `-[:IN_SHELL]->(:Shell)`, `-[:IN]->(:Folder {key: path})` (and the chain `(:Folder)-[:IN]->(:Folder)` up to the home folder, or `/`), `-[:RAN]->(:Program {key: name, path})` for each program of the line, `-[:FOLLOWS]->(:CommandRun)` (the previous Run in the shell); `(:Repo {key: root, remote})-[:AT]->(:Folder)` for a folder in a git repository. A Run's end is `finished_ms`: `ended_ms` belongs to the memory plugin (retired nodes). Command-service Runs are in the shell `service`.
- **Streams**: `shell.<term_id>` (kept ten years), each Run's `started` and `finished` events in order (the record is the `Run` with `event`); `run.<id>.output` (30 days), one record per output line `{at, level, text, ansi?}`, where line `n` is offset `n`. At most 50 MiB of text is kept per Run; lines beyond it are counted.
- **Writes never block a shell.** Runs, events and lines wait in an in-process outbox that a writer task sends every 200 ms (sooner past 2000 lines): one `memory.graph.put` per batch with each Run and its edges, one `memory.stream.append` per topic. While the memory plugin is unavailable everything waits in memory (output up to 64 MiB, then lines are counted and dropped) and is sent when it answers; `terminal.runs` then shows the waiting Runs. A refused Run is retried alone, then without its session link, then with only the edges that place it.
- **Reads**: `terminal.runs`, `terminal.places` and `terminal.habits` are Cypher over the CommandRun nodes; `terminal.run.output` and `terminal.run.histogram` read the Run's output stream (only the window when there is no filter). Completion's history suggestion, the "first time anything like this ran here" check and `usual_ms` use an in-memory index of the history read from the graph once per start.
- **Earlier versions** kept `runs.db` and `runs/<id>.zst` in the data folder. The first start imports them (`src/migrate.rs`), oldest first, checks that the graph and the streams hold every Run, event and line, then deletes the files. An interrupted import is simply run again: the graph merges, and the streams get only what they lack.

## Habits and memory

`terminal.habits {cwd, limit}` returns the commands used in the folder and the folders above it (up to the home folder): Runs, share with exit 0, median duration, last time, plus `notes` learned into memory. After Runs finish (once the terminals have been quiet for 20 s, at most every 3 minutes) the plugin writes per-folder facts to the memory plugin with `memory.knowledge.upsert` (global scope, kind `fact`, source `inferred`, by `terminal`, the folder as alias): `place <path>: habits` ("In ~/dev/web-api you usually run `make dev` (12 runs, ok 92%)", commands with at least 3 Runs) and `place <path>: fix for <command>` (a command that failed, then passed within 10 minutes after another successful command: "... `cargo test` failed 3 times and then passed after `docker compose up -d db`"). The same name updates the same item; a fact the user withdrew stays withdrawn. `terminal.places` adds the folders memory knows to those of the Run store.

Shell integration (zsh, bash 4.4+, fish 4) is injected from `data/shell` without editing the user's startup files (fish runs with `fish_features` `no-mark-prompt,no-query-term`: our marks carry the nonce, and no fish waits for terminal answers while no window shows the pane); after the user's files ran it sets `PAGER=cat` and `GIT_PAGER=cat` (unless `CORTEXTERM_KEEP_PAGER=1`), since the window shows each command's output itself. Output lines are stored stripped and, when they had colour, also with their SGR codes (`OutputLine.ansi`); its marks (OSC 133, 7, 633;E with a per-terminal nonce, and our 6973 PATH/alias/function reports) give `terminal.state` and the Runs (`terminal.run.started` / `terminal.run.finished`), kept in the memory plugin's graph and streams (below) and served by `terminal.runs`, `terminal.run.output`, `terminal.run.histogram` and `terminal.places`. `terminal.assess` (kind and risk, in code), `terminal.complete` and `terminal.file.read` / `terminal.file.write` (the native editor) use the terminal's folder, PATH and aliases.

The paste guard (`src/threat.rs`) is plain code: it decodes a command layer by layer (base64 and hex words, `\x..` and octal escapes, `sh -c`, `eval`, `osascript -e`, `python -c`, `$(...)`, AppleScript's `do shell script`, Unicode tag text) and looks for the macOS stealer and ClickFix shapes (a download or a decoder piped into a shell, fake password dialogs, quarantine removal, disk images and programs run from temp folders, `dscl -authonly`, keychain reads, reverse shells, AI agents started without their checks, raw-IP and drop-service hosts), secrets flowing into the network (`cat .env | curl -d @- …`), and hidden text (zero-width and direction characters, Unicode tags, terminal codes, look-alike letters in web addresses). `terminal.assess` carries its findings as `threats` (any makes the input not safe and `unknown`; `pasted: true` reads encoded and many-step commands stronger) and adds "first time anything like this ran here" when a command's shape (program, subcommand, flags) is new to the Run history. `terminal.scan {text, pasted}` runs the guard alone. Over the network, never from `assess`: `terminal.script.fetch {url}` downloads the script a `curl … | sh` would run (as curl, the first 200 KB kept, never run) and scans it; `terminal.packages.check {text}` looks the packages an install names up in OSV (`MAL-` ids are known malware). `terminal.sandbox.wrap {term_id, command}` returns the `sandbox-exec -f <profile>` line that runs a command in the shared write sandbox with SSH and cloud keys, keychains, browser profiles and wallets unreadable (macOS). `terminal.run.output` and the command service's output are cleaned before anyone reads them: escape codes, control characters and invisible Unicode removed (`OutputLine.hidden` marks a line that had them).

One self-contained plugin folder, separable into its own repository (only `cc-protocol` and `@cortex/sdk` come from outside):

| Path | What |
|---|---|
| `plugin.toml` | identity, build commands and outputs, UI packages and their slots, shell modules, source location |
| `data/shell/` | the shell integration scripts (zsh `.zshenv` + `cortexterm.zsh`, bash `cortexterm.bash`, fish `vendor_conf.d/cortexterm.fish`) |
| `backend/` | Cargo workspace (depends on `cc-protocol` by path), binaries `cc-terminal` (category `terminal`, contract `terminal@1`) and `cortexd` (the PTY daemon, packed as an asset beside it) |
| `ui/` | one npm workspace (own `package-lock.json`, `@cortex/sdk` as a local dependency): `ui/pane` (pane.terminal@1); each package builds `dist/` with `manifest.json` |

## Build and run

```sh
cd backend && cargo build --release && cargo clippy --all-targets -- -D warnings
cd ui && npm ci && npm run build && npm test     # after the SDK is built (cd ../../ui/sdk && npm run build)
cortex-pack build plugins/terminal                  # -> plugins/terminal/target/terminal-<version>-<target>.ccplugin
```

`cortex-pack build plugins/terminal --install` packs the folder into a `.ccplugin` that the frame installs (`frame.plugins.install`), which hot-swaps the backend and the UI package together; Settings > Plugins disables and enables the whole plugin.
